# Local release candidate checklist

This guide describes validation and packaging for the release candidate.
The GitHub repository is `David1726/vla-preflight`. Publication there does not
imply full-model or robot validation. No PyPI release or upstream outreach is
performed by the checks in this guide.

## Reproduce local checks

From a clean source directory with Python 3.12:

```sh
python -m pip install --index-url https://pypi.org/simple -e ".[dev]"
python -m pip install --index-url https://pypi.org/simple wheel
python scripts/release_check.py
```

This checks lint/format, core tests, dependencies, all demo expectations, the
capture example, wheel/sdist build, metadata rendering and package contents. It
does not upload anything. It uses new `release-check-output` and
`.cache/release-check-output-example` directories.
The build uses installed build tooling (`--no-isolation`) so it can run without
fetching build dependencies after setup. For another run choose a new output
directory with `python scripts/release_check.py --out another-release-check`.

Then run the optional original upstream checks following
[integrations.md](integrations.md). Keep their source hashes and license files.
Confirm a separate install of the built wheel runs the CLI/demo without Torch;
the actual first run evidence is in `docs/evidence/wheel-smoke.json`.

## Before publishing (owner checks)

- [ ] Open the actual generated HTML in a local browser. Test the search/status
  filters, evidence expansion, camera thumbnails, plots, local JSON links and a
  narrow viewport. **Browser visual QA remains outstanding in this session**
  because automated local-file navigation was blocked.
- [ ] Read the source, evidence and limitations; decide whether the current
  processor-slice compatibility is sufficient for the intended announcement.
- [ ] Check the intended repository/package name and choose your release metadata.
  `vla-preflight` is a working name, not a reservation or availability guarantee.
- [ ] Review attribution and licenses, and verify only synthetic/shareable traces
  are included. The prepared source bundle excludes environments, caches, Git
  internals, build files and private workspace paths from its filenames.
- [ ] Run the supplied workflow in your repository and replace any version
  assumptions with actual results. Local Windows checks are not Linux CI.
- [ ] Keep the first announcement concrete: CPU demo, original broker/processor
  coverage, seeded failures and limitations. Do not claim generic robot safety,
  a measured real-world detection rate or a guaranteed number of stars.

## Packaging outputs

`dist/` contains the wheel and sdist, plus a source ZIP for manual GitHub import.
The source ZIP is generated by `scripts/package_source.py`; it includes source,
tests, docs, example reports, CI and pinned original fixtures/licenses. It has no
virtual environments or root workspace materials. Build hashes are recorded in
`docs/evidence/release-check.json`; source ZIP hashes are in `dist/source-manifest.json`.
The environment freeze is sanitized evidence, not an installable dependency lockfile.
The sdist omits build logs and its own checksum receipt to avoid embedding stale
or self-referential build evidence. The GitHub source ZIP contains the complete
current local evidence; runtime code and upstream fixtures are present in the sdist.

To regenerate the illustrated walkthrough from current demo data, install Pillow
(`python -m pip install Pillow`) in your maintainer environment, then run
`python scripts/render_walkthrough.py --demo demo-output`. This draws from actual
arrays/results and deliberately labels the frames as illustrations.

Do not upload the whole working folder: it also contains ignored local environments
and generated traces. If you later change code, rerun checks and regenerate
the illustrated walkthrough and example reports from the new actual outputs.
